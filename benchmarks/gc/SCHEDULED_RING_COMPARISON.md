# Persistent ring scheduled-arrival screen

This separate protocol retains the shared v9 workload bytecode, 257 replacements per call, one admitted Program and one attached canonical heap/context across warmup and the offer interval. Canonical managed payload remains 64 MiB, reserved catalog charge is disclosed separately, peers retain 64 MiB Xms/Xmx, and the unchanged envelope is two CPUs / 512 MiB cgroup memory. Workload admission schema 3 (`shared_heap_scheduled_v1`) and sample-plan schema 2 keep prior dedicated/shared invocation schemas unchanged.

Each process warms with 100 calls, then receives a deterministic logical FIFO at a predeclared integer rate for a fixed integer number of seconds. Request i is due at `start + floor(i * 1e9 / rate)`. Offered work is `rate * seconds`, calculated independently of the consumer. The number already offered at elapsed t is `min(offered, ceil((t+1)*rate/1e9))`; the extra nanosecond handles floor-rounded release times. No producer iteration, completion or allocation controls arrivals. The queue is arithmetic and constant-memory, not a growing collection of request objects. This is one serial consumer, not concurrent Java mutators or an external network generator.

No new call starts at or after the offer deadline. An in-flight call may finish afterward. `deadline_completed`, `deadline_backlog`, `after_deadline_completions` (at most one), and unstarted `unfinished` are separate. `peak_backlog` and progress rows count waiting requests, excluding the in-service request; `deadline_backlog` counts all incomplete requests at the deadline, including the possible in-flight request. There is no hidden post-deadline request drain or dropped-work truncation. The offer clock stays open through the deadline even when the last offered call finishes early. Final context detach, payload drain and catalog refund follow outside the schedule clock. A completion cap is explicit invalid evidence, and watchdog/process failures cannot supply capacity bounds.

Service latency covers invoke; response latency starts at its scheduled due time. Two 4096-bin histograms use the existing GcBench upper-bound representation (exact microseconds through 1024, then 64 bins per doubling). A preallocated 128-row completion-relative timeline preserves bounded progress observations. Neither is a complete event stream. Histogram/timeline updates and scheduler checks contribute to later response delays. Native/WASI sleep/yield and HotSpot Thread.sleep/yield share the >=1 ms sleep policy but have different host implementation costs. These costs are not assumed zero. This observer needs separate overhead characterization before qualification.

The driver retains exact checksum totals, logical allocation/release/helper/native-slice totals, all seven compiled method censuses, one-time preparation and final drain, four passive primary-cycle observations around the actual schedule clock, and source/PID/executable/cgroup/lifetime resource receipts. Peer GC bean counters bracket the schedule and retain each collector category separately; no counter sum becomes a fabricated cycle or pause measurement. Missing/zero peer GC activity remains explicit. Ordinary peer timing disables compilation/GC logs. The workload classes are copied without recompilation; only the peer observer changes.

`prepare_scheduled_ring.py` freezes inputs and a fixed-rate pilot or adaptive search without executing work. `run_scheduled_capacity.py` reuses `capacity.py` expansion, contraction, bisection, inconsistent-point handling and endpoint confirmations, plus the established v2 process/resource launcher and independent checker. Every fork remains separate; there is no pooled percentile. Default screen limits remain the existing capacity tool's 1,000 us histogram p99.9, 10,000 us backlog time and 10,000 completions. Short low-rate pilots will fail that sample floor and cannot establish a bracket. They still expose deadline backlog and service/response distributions for protocol evaluation. Any alternative screening limits must be explicitly frozen before the run, and do not change qualification budgets.

A fixed pilot can observe low and high rates without adapting away inconvenient results. It reports a process pass only for valid execution, distinct from screen pass/fail/invalid. Adaptive searches cannot use invalid points as overload upper bounds; low-rate failures cannot be hidden by high-rate successes. Separate longer confirmations need sufficient completions, observed collection exposure, memory/backlog histories and stable behavior. No p99.9/p99.99 confidence claim, sustainable capacity, global-pause capture, three-hour or 24-hour gate follows from this finite lane. Global capture completeness and qualification stay false.

The first coordinated run completed all 60 medium-ring forks at 16, 32, 64 and 128 arrivals/s for ten seconds each. Every fork passed execution validation. The completion floor remains unmet in every fork. [Results and graphs](CANONICAL_MEASUREMENTS.md#first-scheduled-arrival-peer-comparison).
