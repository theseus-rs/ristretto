# Finite retained-ring comparison harness

Schema-2 runs additionally preserve [child lifetime resource receipts](PROCESS_RESOURCES.md)
bound to the exact PID and controller source. Linux wait4 records RSS maxima and
CPU usage across launcher/startup/warmup/execution/teardown, including any reaped
descendant accounting. This is neither measurement-window RSS nor a process-tree
total. WASI observations describe its host. The original schema-1 baseline and
optimized comparison retain unavailable RSS evidence; cgroup charged memory
alone does not establish process RSS.

The shared classfiles are the exact `canonical-ring-v2` fixture. The native compiled/interpreted and WASI interpreted driver admits the same two classfiles that the G1/ZGC peer classpath loads. Only `CanonicalRingPeer.java` is compiled for the peer observer. The independent index-ring model supplies every expected checksum; the compiler census checker retains all seven methods, including unexecuted constructors/size wrappers.

`ring_compare/` is a separate Rust workspace with experimental canonical execution enabled and service recording disabled at compilation. Ordinary `run` is the measured operation. Its `full_invocation_v1` scope begins before canonical heap/frame setup and ends after return, cleanup, and the invocation's local teardown. Classfile admission, compilation, input hashing and final prepared-program destruction are reported separately. Samples and output are allocated/prepared outside invocation clocks. The complete method census is read only at idle boundaries before warmup, before samples, and after samples. Per-method entries/backedges must match the ring model and the sums of invocation counters; aggregate entries alone are insufficient.

HotSpot's `workload_call_deferred_gc_v1` includes the shared workload call and observer dispatch but retains the JVM's heap between calls. It does not force collection at the end of each invocation. Its GC bean snapshots bracket the entire sample batch, including driver gaps, and preserve each bean's name; they do not prove collection inside an individual timed call and must not be summed into an invented cycle count. Canonical release counts are logical reclaimed slots, not completed cycles. The ordinary canonical driver reports completed cycles as unavailable.

These are different collection lifecycles. The graph labels both scopes and includes preparation data in its accompanying raw records. It does not claim body-only throughput superiority, a fixed G1/ZGC ratio, sustainable completed throughput, scheduled p99.9/p99.99, zero global pauses, or any J0–J5 acceptance gate. Recorded `entry_body_v1` diagnostics use the separate `service_capture` binary and its explicit body boundary, excluding setup/cleanup and including recorder cost. Keep those packets separately labeled; never subtract their timings from another invocation or merge them into the ordinary-run graph. The frozen canonical service exporter and its independent checker remain the supported finite body-diagnostic path; this matrix does not silently substitute an unrecorded body timer.

The peer has distinct modes: `check` produces no timings/allocation/GC observations; `allocation` reads actual current-thread allocated bytes around repeated calls but produces no timing; `measure` records invocation times without allocator counters. Every measured peer fork is preceded by a fresh allocation fork using the same observer/bytecode/JDK/configuration and 100 warmup invocations; three counted invocations suffice for the separate allocation lower-bound check. Ordinary timing uses 30 samples per fork. The checked lower bound counts required payload-array bytes, not all object headers, survival, retention or collector throughput. Allocator diagnostics for canonical execution use the separate allocation-count driver; they are not enabled in this comparator.

Build with `build_ring_comparison.py --source SOURCE --target-dir UNIQUE_TARGET --output NEW_BUILD --target native --compiled` and once with `--target wasm32-wasip2`. The default profile is release. Each build freezes the clean source tree, excludes Cargo targets, copies the compiler-reported executable outside targets, and rejects changed source. Use only a clean declared source snapshot: never point this freezer at a busy developer checkout containing IDE/node_modules/generated outputs. Build the peer with `build_ring_peer.py --source SOURCE --source-build NATIVE_BUILD --jdk JDK --output PEER_BUILD`; it preserves the relevant JDK artifacts and exact shared classfiles.

`prepare_ring_comparison.py --native-build NATIVE_BUILD --wasi-build WASI_BUILD --peer-build PEER_BUILD --output PLAN --check` creates a finite untimed matrix. `run_ring_matrix.py PLAN --wasmtime WASMTIME` runs it. A separate `--warmup-check` plan executes the full 100+30 invocation shape without invocation timers, allocator/GC observations or census snapshots; it emits only correctness/cleanup completion. Its supervisor records whole-child wall time solely to size a watchdog, including startup/hashing/compilation/teardown. This is not invocation performance data. Checks use seven replacements, no warmup, one invocation/fork; their clocks and allocator observations remain null. No measurement execution is implied by building or preparing a plan.

For a separately coordinated quiet-host measurement, omit `--check`, freeze steps/warmup/samples/forks/workloads and the per-process watchdog (120 seconds by default) and provide `--resources FILE`. The JSON resource envelope contains sorted `cpu_affinity`, `cpu_quota_us`, `cpu_period_us`, `memory_max_bytes`, and `pids_max`. All runtimes use the same limits. Execution requires a writable delegated cgroup-v2 parent through `run_ring_matrix.py --cgroup-parent PATH`; the launcher applies affinity, enters a fresh child cgroup, reads back CPU/memory/PID limits, writes its actual PID/command and then execs. The parent preserves resource counters/peaks after exit. The host-process budget includes JVM/Wasmtime/runtime memory, while the managed-heap/catalog configuration remains explicit and differs by collector design. Quiescence and ancestor-cgroup competition must be coordinated separately; this tool does not establish host isolation.

The run directory binds exact source archives, build/launch receipts, admission/sample plans, workload bytes, executable and host executable. WASI guest PID remains unavailable, with the real Wasmtime host PID retained. Java injection environment variables and loader overrides are removed from these controlled launches. GC/safepoint/compilation logging is disabled in ordinary timed peer forks. Separate check/allocation diagnostic forks retain those logs; their collection or compiled-method evidence must not be attributed to a timed process. Batch GC-bean snapshots remain outside invocation clocks in timed peers. Observer overhead for these snapshots, clocks and idle canonical census reads still requires a separate evaluation. Failed/checker-rejected forks preserve raw artifacts and stop the matrix. `plot_ring_comparison.py PLAN --output FIGURE_PREFIX` revalidates the completed measured matrix and fresh peer allocation forks before generating standalone SVG/PNG and JSON; it refuses untimed checks. It shows fork medians and raw samples remain available. It does not estimate extreme percentiles from a small sample set.

The append-only service recorder still cannot support 24-hour logging within fixed memory limits. Its bounded streaming/aggregation design, observer-overhead evaluation, genuine in-body collection exposure, complete global/equivalent-pause sources, frozen acceptance budgets, three paired hours and a separate 24 hours remain separate qualification work. The current harness is exploratory and always reports `qualification=false`.

## Distinct persistent-heap protocol

`--shared-heap` selects the schema-2 [persistent-heap protocol](SHARED_RING_COMPARISON.md).
It retains one canonical heap/context across warmup and samples, with explicit payload/catalog
limits, final workload cleanup and independently checked primary-cycle batch observations.
The default schema-1 dedicated-heap protocol and its frozen historical captures remain unchanged.
